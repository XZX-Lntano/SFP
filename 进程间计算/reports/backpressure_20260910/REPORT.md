# FIFO 与 batch 槽反压测试，2026-09-10

## 结论和证据边界

本次完成34个实机性能用例（12个插桩直接DPDK、14个端到端、8个无插桩控制）以及24个RTL反压仿真用例。实机测试使用已部署v4固件；没有改动生产RTL、生产桥接器或默认网卡配置。

建议下一版实验采用 **每端口64 KiB输出FIFO、32个batch槽（512个round槽）**，保留16 rounds/frame。此组合在仿真中通过正常输入、30/120 µs输出暂停、120 µs单worker偏斜，所有64批结果四口均正确。它是提高突发容忍度的候选配置，不是经过上板验证的10G提速保证；尚未综合、布局布线或替换固件。

目前没有实机证据证明16 KiB PL输出FIFO已成为稳态吞吐瓶颈。当前bitstream没有导出FIFO水位、反压周期、聚合丢弃/过期计数：fpga_core.v中对应端口未连接，不能从PS读取。本报告的PL水位、停顿、占用数字全部来自明确施加压力的RTL仿真，不是ILA或板上计数器实测。

## 实机窗口扫描

四个rank固定CPU0..3，端到端客户端CPU4；4 workers、16 rounds/frame、8192字节唯一有效结果。有效带宽不把四份广播结果重复计数。直接测试每例100000批，正序/逆序两次；端到端每例3秒。

直接DPDK诊断副本记录每batch RTT、轮询间隔和burst大小。计时插桩会增加开销，所以另做无插桩对照。正式实机矩阵开始时，首轮RTL仿真已经结束，两类负载没有重叠。

|---:|---|---|---|
|1|1.750 / 1.735|37.418 / 37.749|1.022|
|2|2.422 / 2.437|54.069 / 53.750|1.796|
|4|4.051 / 4.020|64.560 / 65.022|2.449|
|8|5.978 / 5.924|86.939 / 87.739|2.884 / 2.971|

窗口8→16时直接DPDK已经进入平台区，RTT约翻倍，而吞吐没有翻倍。端到端8→16仍有小幅收益，但也远非线性。

纠正此前解释：W×payload/RTT可以用于估算所需在途数据，但RTT会随排队和窗口增大。W=16、RTT约292 µs算得3.59 Gbit/s，与观测相符不能单独证明“16槽就是根因”，也不能保证44/64个batch就能达到10G。要测32/64窗口，需要匹配的硬件槽位和软件索引/代际步长，不能只改CLI超过16。

## 主机RX环对照

初始RX64使用511个mbuf，RX512使用2047个mbuf；这组同时改变了内存池大小，不能作为纯描述符深度因果对照。因此另编译无每包计时插桩的原benchmark循环，RX64/RX512均固定2047个mbuf，TX128、cache32相同，每例200000批，两次且交换顺序。

|RX描述符|窗口|有效Gbit/s，两次|
|---:|---:|---|
|64|8|5.740 / 5.826|
|64|16|5.843 / 5.870|
|512|8|5.866 / 5.880|
|512|16|5.891 / 5.798|

RX512没有稳定而显著的吞吐收益。全部本次实机用例的四口missed、errors、no_mbuf、rejected、short_bursts均为0。不能因此保证无限时间无丢包，也不能因吞吐相近断言所有硬件资源都没压力。此次不建议把RX环强行改成512作为带宽优化；扩大软件窗口后可以再测试RX128/256的抗调度抖动效果，并同时增加mbuf预算。

主机RX环、PL收发FIFO和BRAM聚合槽是三种不同资源。主机不轮询通常只让NIC RX环积压/丢包；未经验证启用以太网流控，不能把暂停主机RX等同于PL的tready反压。本次没有用CPU暂停冒充硬件反压实验。

## RTL压力模型

直接实例化生产axis_udp_batch_aggregator、axis_broadcast和axis_async_fifo。当前同宽axis_async_fifo_adapter数据路径使用的就是该FIFO；参数匹配生产TX配置：FRAME_FIFO=1、RAM_PIPELINE=1、DROP_WHEN_FULL=0。聚合时钟300MHz，输出时钟156.25MHz；每帧1046个64位beat，帧间输出留3周期，近似10G线速。

每个worker发送64个16-round完整批次，周期2015个300MHz周期（6.7167 µs），在输入侧用已提交整帧以300MHz突发读出的方式驱动聚合器，近似现有RX帧FIFO输出。不包括RX异步FIFO、完整MAC/PCS、PS、MPI或NIC；因此不能给出实际RX FIFO水位结论。数值按worker/round/entry/batch变化，四个出口逐字节与独立Python求和结果比较。所有收到的帧均无数值错误、重复或半帧。

压力场景：

- 四个worker同步、无额外输出停顿。
- 仿真60 µs时强制port3下游AXIS暂停30或120 µs；其余出口不停。此为人为tready压力，不是声称真实网卡出现相同PAUSE。
- worker3整条输入流延迟120 µs，其余三路按原速率发送。

发送端是有意不等ACK的开环压力源；在小槽配置中会违反生产协议的槽位信用限制，用来暴露容量边界。仿真丢失批次不能直接解释为生产闭环benchmark会丢包；正确信用机制应先限速。仿真长度约867 µs，小于100 ms过期时间，某些冲突后不完整槽不会在这次仿真内回收。

完整24配置结果见rtl_table.md和rtl_results.json；原始XSim日志在rtl/。

关键发现：

1. 正常近10G输入，16 KiB FIFO峰值8400 B、聚合反压0、占用峰值1个batch，四口各64/64正确。说明该局部RTL模型不需要加深FIFO才能维持稳定输入；不等于整机已达10G。
2. port3暂停30 µs时，16 KiB FIFO顶满，聚合最长连续停顿22.930 µs、槽峰值5；32 KiB仍顶满并出现停顿；64 KiB峰值45760 B，聚合停顿为0、槽峰值1。64 KiB能吸收这次指定暂停。
3. port3暂停120 µs，16 KiB+16batch仅收到48/64；32 KiB+16batch收到64/64但槽占用到16，没有余量。64 KiB+32batch全部正确，FIFO会满，槽峰值12，仍有输出反压。64 KiB不是任意长暂停的解决办法。
4. worker3晚到120 µs，16个batch槽无论FIFO16/32/64 KiB均只收到16/64；此时FIFO峰值仅约8.4 KiB且聚合输出反压为0。扩大FIFO无效。32个batch槽收到64/64，占用峰值19；64槽同样正确但此次没有额外收益。

## 建议参数与实施边界

|参数|当前|下一版建议|理由|
|---|---:|---:|---|
|聚合输出后的每口TX FIFO|16384 B|65536 B|吸收模型中的30 µs单口暂停，降低广播共享反压|
|聚合RX侧FIFO|16384 B|暂保留|本次没有RX水位数据，不能据TX压力盲目加深所有FIFO|
|round槽|256|512|32个batch覆盖本次19槽偏斜峰值，并给软件窗口扩展空间|
|软件batch窗口|上限16|匹配新固件后扫描8/16/24/32|找平台区，不默认越大越快；各处槽索引需匹配32槽|
|主机RX描述符|64|本次保持64|RX512对照无稳定提速；更大窗口再测缓冲需求|

不要仅将共享SWITCH_FIFO_DEPTH改成65536，因为它同时被多处RX/TX FIFO使用。应拆出TX深度参数，定向加深四个输出FIFO。同步修改所有槽掩码、代际步长、请求ID分配和客户端最大窗口，继续保留每槽标识检查和限额信用。

粗略容量关系：10G约每微秒1250字节，额外暂停T需要约1250×T字节缓冲，再加一帧及流水线余量。30 µs对应37500 B，加8368 B约45868 B，因此64 KiB合理。worker偏斜120 µs / 6.714 µs约17.9帧，再计入在处理的一帧，仿真测得19个槽。

512 round槽此前完整工程BRAM估算571.5/912，不含这次TX FIFO扩容的额外开销；当前457.5/912为已实现结果。必须重新综合、布局布线与检查时序，才能部署新配置。此次没有验证更大配置时序，不能把估算写成实测资源。

后续板上确认需要在下一版加入：每口FIFO水位峰值/溢出/帧计数、聚合valid&&!ready周期及最长连续值、槽占用峰值、各worker丢弃原因、过期计数，经CDC后以一致快照暴露给PS CSR。然后在相同输入速率下比较16/32/64 KiB与16/32batch。现有mqnic通用TX/RX FIFO深度寄存器描述的是网卡DMA路径，不等于自定义聚合旁路的SWITCH_FIFO_DEPTH。
